## Note de tour 1 — UX Designer — `moteur-interprete` (n°10)

**RISQUE** — Le brief pose un champ libre « player-facing » sur un écran qui porte déjà la Console (registre développeur-débogueur, `ALLER <lieu_id>`, mono, vocabulaire technique CLOS — veto explicite dans `design_contract.console_hors_runtime` de `moteur-dossier`). Si le champ libre se glisse *dans* `ConsoleCommandes.tsx` ou en hérite le style, l'écran devient un panneau de debug déguisé en fiction : exactement la dérive que n°9 avait anticipée et nommée dans son propre `design_contract` (« c'est la surface par laquelle un canal d'entrée en texte libre s'installerait sans qu'aucune revue le voie »). Second risque : `Chip` (suggestions cliquables) est listé dans `DESIGN-SYSTEM.md` mais **n'existe dans aucun fichier de `src/brain/components/`** — seule une référence `.jsx` dort dans `design_handoff_gamebook_editor/`. Un ouvrier pressé le recodera en composant maison inline plutôt que de le construire comme primitive.

**OBJECTION** — Le champ libre ne peut ni remplacer ni habiter la Console : ce sont deux registres et deux publics (l'auteur qui teste vs le joueur qui vit la fiction). La Console doit rester un outil de test réservé, visuellement démoté (encadré pointillé, libellé « CONSOLE (débogage) »), jamais supprimée à cette itération (R1 route encore uniquement vers `COMMANDES` = `aller` seul) mais **jamais la même boîte** que le champ « QUE FAITES-VOUS ? ».

**PROPOSITION** — Nouveau composant `PlayerInputBar` (`src/features/play-mode/components/`), Field non-mono, `Entrée` soumet, `Échap` vide sans fermer d'écran. Trois `Chip` cliquables sous le champ (à construire — premier consommateur réel, domicile `brain/components/` puisque suggestions et console pourraient un jour partager un composant transverse). Sortie R3 (`recit`) rendue via un bloc de prose au registre joueur (variante d'`OutcomeBlock`, jamais le style `metaJournal`) ; le journal garde `role: 'joueur'|'moteur'` mais aucune valeur mono n'apparaît dans le fil visible du joueur.

**VERDICT** — Pas de veto. Objection forte : je bloque l'admission d'un champ libre qui réutiliserait `ConsoleCommandes` ou son style mono comme surface joueur.

### Contrat de design — `PlayerInputBar` + `SuggestionChips` + bloc de récit R3

**Composants réutilisés** : `Field` (non-mono, `id="player-input"`, `autoFocus` selon le même patron `key={session.horloge.tour}` que `ConsoleCommandes`), nouveau `Chip` (primitive `brain/components/`, à construire : glyphe optionnel + texte, `tone` par défaut neutre, `onClick`), `OutcomeBlock`-like pour le récit (variante *sans* nouvelle prop `variant` tant qu'aucun jet n'existe — même contrainte que l'it1 de `moteur-dossier`, D-18).

**Textes exacts** :
- Libellé du champ : `QUE FAITES-VOUS ?` (mono, majuscules, registre interface — désigne l'action sans en faire partie, même patron que `entete` d'`OutcomeBlock`).
- Placeholder : `Décrivez ce que vous tentez…` (amorce, jamais vide).
- Bouton (si le formulaire en porte un, sur le même patron que `EXÉCUTER`) : `ENVOYER`.
- État vide des suggestions (avant le premier tour, ou si R3 n'en produit aucune sous budget dégradé) : pas de bloc vide — les 3 `Chip` sont simplement absentes ; aucun texte de remplissage ne doit inventer une suggestion.
- Message de clarification R1 (`{ clarification }`) : rendu dans le MÊME bloc de prose que le récit, jamais dans la Console — texte fourni par le modèle, contraint par schéma, jamais composé par le composant (Déméter, même règle que `refus` de `ConsoleCommandes`).
- Message de dégradation budget (§2.8 garde-fou 4) : `Le narrateur répond brièvement pour l'instant.` — texte UX à écrire au moment de câbler le budget par tour, pas encore nécessaire en tour 1 de cette feature si aucun budget n'est dépassé.

**États** : défaut (champ vide, focus, 0-3 chips du tour précédent effacées au remontage — mêmes règles que la Console) ; en attente de réponse IA (le champ reste éditable ou se désactive ? — **à trancher en tour 2**, impact ergonomie clavier fort : un champ désactivé pendant l'appel casse la cadence si la latence dépasse ~1s, proposition : ne jamais désactiver, mettre en file) ; erreur/illisible (dégradation → texte neutre, jamais un état corrompu, cf. garde-fou 1) ; suggestions cliquables → remplissent le champ ET soumettent (raccourci, jamais un rail obligatoire, §2.9).

**Clavier** : `Entrée` soumet nativement (un seul `<input>`/`<textarea>` dans un `<form>`, aucun `onKeyDown` maison) ; `Tab` doit atteindre les 3 `Chip` dans l'ordre après le champ, avant la Console reléguée en bas ; `Échap` ne ferme rien (ce n'est pas une modale) mais peut vider le champ — à confirmer en tour 2 avec le rôle interaction.

**Discipline de l'accent** : les `Chip` de suggestion ne portent PAS `--accent` par défaut (ce ne sont pas l'option sélectionnée) — seul un état `:hover`/`:focus-visible` ou un état actif transitoire (chip cliquée en cours d'envoi) peut emprunter l'accent, jamais une décoration permanente.

### Décisions prises en autonomie faute de spécification

- **Le champ libre est un NOUVEAU composant, pas une évolution de `ConsoleCommandes`** → j'ai choisi de garder la Console strictement séparée (démotée, jamais supprimée à cette itération) → si c'est l'inverse (un seul champ qui bascule entre mode debug et mode joueur), le coût est un composant qui porte deux registres de langue dans le même fichier, contredisant directement `design_contract.console_hors_runtime` de `moteur-dossier` sans qu'aucune revue ne l'ait retranché — la faute de registre que ce comité doit justement empêcher.
- **`Chip` est construit dans `brain/components/`, pas dans `play-mode/components/`** → parce que DESIGN-SYSTEM.md le classe déjà parmi les primitives transverses (au même rang que `Badge`, `IconButton`) et qu'un futur usage dans une autre feature (ex. tags d'indices) est plausible → si c'est l'inverse (composant maison local à `play-mode`), le coût est une primitive dupliquée le jour où un deuxième consommateur apparaît, KR-109 rouvert en dette au lieu d'être réglé au premier geste.
- **La sortie R3 (`recit`) n'est PAS ajoutée comme un troisième style dans `JournalRow`** → j'ai choisi un bloc de prose séparé, au-dessus du champ de saisie, dans le même esprit qu'`OutcomeBlock` pour le texte d'ouverture → si c'est l'inverse (tout passe par le journal, y compris la narration), le coût est la confusion du CONSTAT (journal, immuable, développeur-lisible) avec la FICTION (prose vivante, relue par le joueur), et `JournalRow` perd la propriété que sa docstring revendique (« un constat, jamais une entrée du rejeu »).
- **Le champ ne se désactive jamais pendant l'appel IA** → priorité donnée à la cadence clavier (règle 6 de mon mandat) plutôt qu'à un verrou anti-double-soumission classique → si c'est l'inverse (champ désactivé le temps de la réponse), le coût est un défaut d'ergonomie mesurable sur toute latence perceptible, à trancher formellement en tour 2 avec le rôle interaction/ergonomie clavier plutôt que tranché seul ici.

### Proposition ESLint (à discuter avec le tech-lead)

Règle supplémentaire ciblant `src/features/play-mode/**` et le futur `src/player/**` : interdire l'import de `ConsoleCommandes`/`JournalRow` depuis tout fichier dont le nom ou le chemin contient un futur marqueur "joueur final" (à définir avec le tech-lead selon où vivra l'écran shippé) — pour empêcher mécaniquement qu'un import de la Console traverse la frontière registre-développeur → registre-joueur. Motif : le même que `no-restricted-syntax` sur les hex — un veto qui ne dépend pas de la vigilance d'un ouvrier.
